The user problem

A form alone cannot show where work stands.

Someone reporting an issue needs to know it has an owner and a status. A technician needs enough context to act. The system therefore has to preserve both responsibility and state through the full request lifecycle.

My ownership

Build the workflow from intake to closure.

I built the full-stack application, including request creation, technician assignment, status changes, and queue filtering. I owned the technical implementation and the workflow rules represented in the interface and API.

Product decisions

Make ownership and status visible.

I centered the experience on four tasks: create, assign, track, and find. The application requires a technician before resolution and prevents changes after closure. Those rules keep the displayed status consistent with the underlying work.

Delivery

Make the rules testable.

I designed REST APIs and a layered Controller–Service–Repository architecture with JPA/Hibernate persistence and validation. The React interface supports intake and technician management, while JUnit and Mockito tests cover key service rules. The repository documents the API and local setup.

How I would evaluate it with users

Test whether people can submit a complete request, find its owner and status, and identify work that needs attention. These are proposed evaluation measures; the project has no reported user adoption data.

Outcome

A working, testable request lifecycle.

The application connects the frontend, API, and database through the full lifecycle. Its code and setup documentation are public.
